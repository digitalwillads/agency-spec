The Timeline

The shared memory of the system. Every agent reads it before acting. Every agent writes to it after acting. This is how the system knows what's going on.

Why the Timeline Exists

Without shared memory, every agent starts cold. The Communication agent reads Ruthy's email but doesn't know that Monitoring just flagged a conversion drop on Nzymes' account. The Reporting agent drafts a cheerful weekly update without knowing that Admin flagged an overdue invoice an hour ago. Each agent knows its own piece but is blind to everything else.

The timeline solves this. It's the one place where everything that happens with a client is recorded. Every agent reads it for context. Every agent writes to it after acting. The result: no agent operates in a silo, because they all share the same memory.

Core Idea
The timeline is to the agents what institutional memory is to a team. When a new team member joins, they can read the history and understand what's going on. When an agent needs to act on something, it reads the timeline and understands the full picture - not just its own domain's view.

The Guarantees

These are the properties that never change, regardless of how many agents, data sources, or clients the system has:

Guarantee What It Means Why It Matters
One per client Each client (company) has exactly one timeline. Multiple contacts at the same company share the same timeline, with attribution on each entry. You never have to wonder "which timeline has this?" There's only one place to look.
Append-only Entries are never edited or deleted. New information is added at the end. Corrections are new entries that reference and supersede the original. The timeline is a permanent, auditable record. You can always see what happened and when. Nothing gets quietly rewritten.
Chronological Entries are ordered by time. Most recent at the bottom (or top, depending on the view). Reading the timeline tells a story. You can follow the narrative of a client relationship from beginning to now.
Cross-domain Every domain writes to the same timeline. Communication, Monitoring, Actions, Reporting, Admin - all in one stream. An agent can see the full picture, not just its own domain's slice. The Reporting agent sees monitoring alerts alongside client emails alongside billing events.
Attributed Every entry records who or what created it - which agent, which team member, which domain. You can always trace an action back to its source. "Eddie sent this email." "The monitoring agent made this change." "Will approved this report."
Linked to source Every entry has a link back to the original - the email thread, the meeting recording at the timestamp, the ad platform change log, the invoice in Stripe. The timeline entry is a summary. One click takes you to the full original. You never have to go hunting for context.

What Gets Recorded

Every entry has the same structure: when it happened, what happened (the event type), who did it (attribution), a description in plain language, and a link back to the source - the original email thread, the meeting recording at the relevant timestamp, the ad platform change log, the invoice in Stripe. The timeline entry is a summary, but one click takes you to the full original.

The event types grow over time as the system adds new capabilities. Today's list is a starting point - not a ceiling. What matters is the consistency: every event follows the same structure, so agents and queries work the same way regardless of the event type.

How Agents Read the Timeline

A client who's been active for two years could have thousands of timeline entries. An agent processing a single email doesn't need all of them. The system provides bounded reads - each agent reads a window of relevant history, not the full log.

The principle: read enough to have context, not so much that you drown in it.

Agent Type Default Window Why This Window
Communication Last 30 days of communications + active tasks Needs recent conversation context to draft relevant replies
Monitoring Last 7 days of changes + recent monitoring actions Needs to know if a recent change explains an anomaly
Reporting Last 90 days Needs the broader arc for periodic summaries
Task thread (on demand) Loaded as the conversation requires User might ask "what happened last quarter?" - agent pulls what's needed

These windows are defaults. An agent can go deeper if the conversation demands it. But the default prevents an agent from burning context and cost on irrelevant history during routine processing.

How Agents Write to the Timeline

Every agent writes to the timeline after it acts. This is not optional - it's how the system maintains its shared memory. The rule is simple:

Invariant
The timeline records things that are meaningful to the client relationship. Not everything that passes through the system. A vendor newsletter that isn't relevant to any client doesn't get logged. A "thanks!" reply that adds nothing to the story doesn't get logged. TrashMan filters outright junk before anything sees it. The Communication agent makes the second-level judgment: is this worth recording in the client's history? If it wouldn't help an agent or a human understand what's going on with this client, it stays out of the timeline.

Some entries are written automatically (a client email arrives, it's logged). Some are written as a consequence of agent action (monitoring auto-fixes a budget, the fix is logged). Some are written by the user (you approve a report, the approval is logged). But not everything makes it in - the Communication agent filters out messages that don't add meaningful context to the client relationship. A payment receipt confirmation, a "sounds good" reply, a vendor newsletter - these passed TrashMan (they're not junk) but they're not worth polluting the timeline with. The timeline should tell the story of the client relationship, not be a firehose of every email that wasn't spam.

Corrections, Not Edits

Because the timeline is append-only, you can't go back and change an entry. But agents and humans make mistakes. Wrong attribution, wrong data, misclassified events. The correction model:

  1. The original entry stays exactly as it was recorded
  2. A new correction entry is appended that references the original and provides the accurate information
  3. Any agent reading the timeline sees the correction and uses the corrected data
Example

Entry #4521 (original): "Budget adjusted from $85/day to $52/day on Search - General"

Entry #4538 (correction): "Corrects #4521: budget was adjusted to $62/day, not $52/day"

This preserves the audit trail (you can see what was originally recorded) while ensuring agents act on accurate information. No silent rewrites. No lost history.

The Timeline as Foundation

Every other part of the system relies on the timeline:

  • Communication agents read it to understand client context before responding
  • Monitoring agents read it to check if a recent change explains an anomaly
  • Reporting agents read it to generate accurate periodic updates - and check it before sending to avoid embarrassing mistakes
  • Admin agents write billing events to it so other agents know the financial picture
  • Task preprocessing pulls from it to give the user context when they open a task
  • Cross-agent queries consult it as the source of truth about what's been happening
  • The user can read it directly to prepare for a client call or understand a situation

If the timeline is comprehensive and accurate, every agent is smarter. If the timeline has gaps, every agent has blind spots. That's why the ingestion layer and the "always log" principle matter so much - they ensure the timeline reflects reality.

Future: Narrative Layer
The raw timeline is comprehensive but dense. In the future, an AI-generated narrative layer will sit on top: "Here's where things stand with Nzymes in 30 seconds." A plain-English summary distilled from the event log. The raw log stays as the source of truth underneath. The narrative is a reading aid, not a replacement.
