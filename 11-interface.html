The Interface

One app, one sidebar, one conversation area. Everything you need to run the agency, nothing you don't.

Layout Overview

The interface is a two-panel layout: a sidebar on the left with your task list, and a main conversation area on the right where you work. Dark theme matching the brand. No dashboards, no widgets, no charts competing for attention. Just a list of things that need doing, and a place to do them.

The sidebar is your control surface. The main area is your workspace. That's it. Two panels, one pattern.

The Sidebar

The sidebar is a task list sorted by priority. CRITICAL items at the top (red), then HIGH (orange), then NORMAL, then LOW. Within each priority level, tasks are sorted by age - oldest first, so nothing gets buried.

Each task in the sidebar shows:

  • Client name - who this is about
  • Task title - what it is, in plain language
  • Domain tag - which domain created it (Monitoring, Communication, Setup, Reporting, Admin)
  • Age - how long since it was created
  • Assignee - if it's assigned to a team member

Search and Filters

The sidebar has a search bar at the top. Type a client name, a keyword, or a domain name and the list filters instantly. Below the search bar, filter buttons let you narrow by:

  • Domain - show only Monitoring tasks, only Communication tasks, etc.
  • Client - show all tasks for a specific client
  • Assignee - show tasks assigned to Eddie, Reileigh, Tristan, or Isaac
  • Status - show only open tasks, or include completed ones

Keyboard Navigation and Bulk Operations

The sidebar supports full keyboard navigation. Arrow keys to move through the list, Enter to open a task, Escape to go back to the list. For bulk operations - marking multiple tasks done, reassigning a batch, changing priorities - select multiple tasks with Shift+Click or Cmd+Click, then use the action menu.

Working Tasks

When you open a task from the sidebar, the main area becomes a conversation thread. But it's not an empty chat - the AI has already done work before you arrived.

Preprocessing

At the top of every task thread, the preprocessing results are shown. These are the cross-agent queries, timeline lookups, and data pulls that happened when the task was created. They're displayed as collapsible tool execution cards - green dot for success, red dot for failure.

You don't have to read them. They're context for the AI's draft. But if you want to verify where the information came from - "how does the AI know about the conversion drop?" - the preprocessing cards show exactly which queries ran and what they returned.

Tool Execution Cards

When the AI takes an action during your conversation - sends an email, queries an ad platform, checks a website - the action appears as a tool execution card inline in the thread. Each card shows:

  • What tool was called - "Gmail: Send Email" or "Google Ads: Get Campaign Performance"
  • Status - green dot (success) or red dot (failure)
  • Summary - one-line result ("Email sent to ruthy@nzymes.com" or "CPA: $28.42, Conversions: 38")
  • Details - collapsible section with full request/response data for debugging

Failed tool calls show the error and offer a retry button. If the Gmail API is down, you see: red dot, "Gmail: Send Email - Failed (503 Service Unavailable)", and a retry button.

Communication Task Behavior

Communication tasks (email replies, follow-ups, client messages) have a specific behavior: when you approve and send the message, the task is marked as Done, but the conversation panel stays open. This lets you continue the conversation if the client replies quickly, or if you want to add notes to the timeline without opening a new task.

Ad-Hoc Queries

Not everything is a task. Sometimes you just want to ask the system a question: "What was Nzymes' CPA last month?" or "How many active campaigns does Stone & Tile have?" These are ad-hoc queries.

The interface offers two creation modes:

  • New Task - creates a persistent task in the sidebar. Has preprocessing, appears in the task list, logged to the timeline. Use this for work that needs to be tracked.
  • Quick Query - opens an ephemeral conversation. No preprocessing, doesn't appear in the sidebar, not logged to the timeline (unless it results in a mutation). Use this for quick questions where you don't need a paper trail.

Quick queries are ephemeral by default, but if the conversation leads to an actual change - you ask about CPA and then say "adjust the budget" - the system promotes it to a full task. The mutation is logged to the timeline, and the conversation is preserved. You never lose work because you started in the wrong mode.

Example: Quick Query Promotes to Task

You open a Quick Query and type: "What's ExclusiveMatchmaking's Google Ads CPA trending?"

The AI pulls the data: "$67 this week, down from $82 last month. Trending well."

You follow up: "Great. Increase their daily budget by 20% on the Search - Brand campaign."

That's a mutation. The system promotes the query to a task: "ExclusiveMatchmaking - Budget increase on Search - Brand." The budget change is logged to ExclusiveMatchmaking's timeline. The AI executes the change (after your confirmation) and the task appears in the sidebar for audit purposes.

Mobile

V1 is desktop-first. The interface is designed for a full-size screen with a sidebar and conversation area side by side. That said, it's responsive enough for basic mobile triage.

On mobile, the sidebar collapses to a full-screen task list. Tapping a task opens the conversation in full screen. You can review tasks, approve messages, and mark things done from your phone. You can't do deep work - no complex ad adjustments or multi-step workflows - but you can keep things moving when you're away from your desk.

If TheRealSleep's website goes down at 9 PM and you get the CRITICAL notification, you can open the app on your phone, see the issue, approve the client message, and handle it in 30 seconds.

Notification Preferences

The system is not a notification cannon. By default, only CRITICAL priority tasks push a notification to your device. Everything else waits for you to open the app.

Setting Default Options
Push notifications CRITICAL only Off, Critical Only, Critical + High, All (not recommended)
Quiet hours 10 PM - 7 AM Configurable. During quiet hours, even CRITICAL notifications are silenced unless the issue has been active for 30+ minutes.
Notification sensitivity Normal Low (only site-down and billing emergencies push), Normal (all CRITICAL pushes), High (CRITICAL + HIGH push). Adjustable per client.
Example: Quiet Hours

It's 11 PM. TheRealSleep's website goes down. The system detects it, creates a CRITICAL task, but checks quiet hours - it's on. The notification is held. At 11:30 PM (30 minutes of sustained downtime), the system overrides quiet hours and pushes the notification. A 2-minute blip at 11 PM doesn't wake you. A sustained outage does.

Error Handling

Things break. APIs go down, AI models hallucinate, auto-fixes backfire, deduplication makes a bad call. The system's philosophy on errors is simple: fail visibly, never silently. Every failure surfaces to you with enough context to understand what happened and what to do about it.

Error Type Example System Response
API down Google Ads API returns 503 for 15 minutes Monitoring tasks for Google Ads clients are paused. A NORMAL priority task is created: "Google Ads API unavailable since 2:15 PM. Monitoring paused for affected clients. Will resume automatically when API recovers." Existing tasks show tool cards with red dots and "API unavailable" messages. No false alerts are generated from stale data.
Auto-fix fails Budget reduction API call rejected (insufficient permissions) The auto-fix task is created as HIGH priority instead of the usual "review" task. The tool card shows the failure. The AI explains what it tried to do, why it failed, and suggests a manual fix: "Tried to reduce Stone & Tile daily budget from $85 to $62 but the API returned a permission error. You may need to make this change directly in Google Ads."
AI bad output The AI drafts a client email with obviously wrong numbers This is caught by the human-in-the-loop. Every client-facing message requires your approval. If the numbers look wrong, you edit them or ask the AI to re-pull the data. The AI always cites its sources (tool execution cards), so you can verify where the numbers came from and spot the discrepancy.
System downtime The application itself is unavailable for 2 hours On recovery, the system runs a catch-up sweep: processes all data that arrived during downtime, backdates timeline entries to their actual occurrence time, and creates tasks that should have been created during the outage. Tasks created from the backlog appear in the sidebar as usual.
Wrong dedup merge Two genuinely different emails are incorrectly merged as duplicates The user can split incorrectly merged tasks. The system logs the correction, creates the separate tasks, and re-runs preprocessing on each one. A correction entry is appended to the timeline noting the dedup error. Future dedup rules are refined based on the false positive.
TrashMan false positive A legitimate client email is flagged as junk and filtered out TrashMan-flagged items are quarantined, not deleted. A periodic review task surfaces quarantined items for human review ("3 items in quarantine this week - review?"). If a false positive is found, the email is restored, a task is created, and the TrashMan ruleset is updated to prevent recurrence.
Stale context Agent makes a decision based on timeline data that's 6 hours old Every piece of context shown in a task includes a freshness timestamp. If data is older than expected, the AI notes it: "Note: Google Ads data is 6 hours old (last pull at 8:00 AM). Conversion numbers may not reflect the current state." The user can trigger a refresh to get current data.
Cross-agent query failure Communication queries Monitoring but Monitoring times out The task is created without the Monitoring context. The preprocessing shows a red-dot tool card: "Monitoring query failed (timeout). Campaign performance data unavailable at time of processing." The AI proceeds with what it has and tells you what's missing. You can re-run preprocessing to try again.
Error Philosophy
The system should never fail silently. If something goes wrong - an API call, an auto-fix, a cross-agent query, a dedup decision - the user should know about it. Not in an overwhelming way (a wall of error alerts), but in a contextual way: when you're working a task and something failed during its processing, you see it right there in the tool cards. When something system-wide fails, you see it in the daily digest or as its own task. The goal is: you should never be surprised by something the system didn't tell you about.
