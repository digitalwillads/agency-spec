Ingestion

How data gets into the system, how it's stored, and how agents retrieve it. The pattern that stays the same no matter what we connect to.

The Problem

The agency's data lives in a dozen different places - Gmail, Google Ads, Facebook, Stripe, meeting recordings, text messages. Each has its own API, its own format, its own quirks. An agent that needs to understand a client's situation shouldn't have to know how to talk to all of them. It should just ask: "What's been happening with Nzymes lately?" and get an answer.

The ingestion layer solves this. It sits between the outside world and the agents, handling two jobs:

  1. Pull data in from external sources on a continuous basis
  2. Normalize and store it so agents can read it in a consistent format, regardless of the source

The Pattern

Every data source - whether it exists today or gets added next year - follows the same four-step pattern:

1. Connect

Get access to the data. This is the only part that's different for every source - each API has its own authentication, its own rate limits, its own way of delivering data. Some push to us (webhooks), some we pull from (polling), some we do both. The connection method is an implementation detail specific to each source.

2. Normalize

Transform the raw data into a common format the rest of the system understands. An email from Gmail, a text from iMessage, and a WhatsApp message are all fundamentally the same thing: a message from someone, with content, at a time. They should look the same to the agents that process them.

Key Principle
Normalization makes the format consistent - agents don't need to deal with Gmail API quirks vs WhatsApp API quirks. But the source is preserved as metadata. The agent knows Ruthy sent a WhatsApp message, not just "a message from Ruthy." This matters: it needs to reply on the right channel, and if she reached out via WhatsApp AND email about the same thing, that multi-channel reach-out is itself a signal worth noticing.

3. Store

Persist the normalized data so it can be retrieved later. This is where the timeline comes in (covered in detail on the next page). But the principle is: store once, read many times. Data that enters the system is written to a durable store and then read by as many agents as need it. No agent should have to go back to the original source to re-fetch data that's already been ingested.

4. Retrieve

Give agents a clean way to query what they need. An agent should be able to ask things like:

  • "Give me Nzymes' last 30 days of communications"
  • "What ad changes happened for Stone & Tile this week?"
  • "Is ExclusiveMatchmaking's invoice paid?"
  • "Show me all meetings from last Friday"

The retrieval layer translates these questions into queries against the stored data. The agent doesn't need to know the storage format, the database schema, or which original source the data came from.

Three Types of Data

Not all data is the same. How you ingest, store, and retrieve it depends on what kind of data it is:

Type What It Is Storage Philosophy Examples
Events Things that happened at a point in time. Immutable once recorded. Append-only. Never modified, never deleted. This is the timeline. Emails received, meetings held, invoices paid, ads changed, tasks completed
State The current condition of something. Changes over time. Current snapshot, updated when it changes. History of changes tracked as events. Campaign budget ($62/day right now), website status (up/down right now), invoice status (paid/unpaid right now)
Content Files, documents, media. Larger, less structured. Stored as files, referenced by events. Not stored inline in the timeline. Email attachments, meeting recordings, brand asset PDFs, ad creative images
Example: An Email Arrival

Ruthy from Nzymes sends an email with a PDF attached asking about CPA numbers.

Event: "email_received from Ruthy at Nzymes, April 3, 4:12 PM" - appended to Nzymes' timeline. Immutable.

State: Nzymes' latest communication status updates to "pending response." This is mutable - it'll change to "responded" when you reply.

Content: The PDF attachment is stored as a file and linked to the timeline event. The event says "attachment: Q1-report.pdf" with a reference to where it lives.

When Data Comes In

Some data needs to arrive immediately. Some can wait. The ingestion layer handles both:

Pattern When to Use How It Works
Real-time (push) When delay matters. Client messages, payment events, website outages. The source pushes data to us via webhooks or push notifications. We process it immediately.
Near-real-time (poll) When the source doesn't support push. Email inboxes, sent-mail folders. We check the source frequently (every 1-2 minutes). Close to real-time, but not instant.
Scheduled (batch) When freshness is less critical. Ad performance data, weekly metrics. We pull data on a defined schedule (every 4 hours, daily, weekly). Frequency depends on the monitoring rules that use the data.
Principle
Client messages should appear in the system within minutes. Ad performance data can lag hours. Website outages should be detected within minutes. The ingestion cadence matches the urgency of the data.

Handling Volume

Sometimes a lot of data arrives at once. A new team member's inbox is connected and 10,000 historical emails need ingesting. A client CC's you on a 30-email internal thread. A spam campaign hits an inbox with 200 messages in an hour.

The ingestion layer handles this with three principles:

  • Queue, don't drop. Every piece of data that arrives gets queued for processing. Nothing is thrown away because the system is busy. If there's a backlog, it works through it in order.
  • Most recent first. During a historical backfill (connecting a new inbox), process in reverse chronological order. The most recent messages are the most important and should be available first.
  • Batch from the same source. If one person sends 5 messages in 5 minutes, they're batched and processed as a group rather than creating 5 separate tasks. (The Communication agents handle this batching - see page 05.)

Adding New Sources

The ingestion layer is designed to grow. Today we connect to Gmail, ad platforms, Stripe, and meeting recordings. Next month it might be TikTok Ads. Next quarter it might be a CRM system or call tracking.

Adding a new source means building one new connector that follows the same four-step pattern: connect, normalize, store, retrieve. The rest of the system - the agents, the timeline, the task queue, the interface - doesn't change. It just starts receiving a new type of data in the same format it already understands.

Design Principle
The cost of adding a new data source should be writing one connector. Not refactoring the agents. Not changing the timeline schema. Not updating the interface. One connector, and the entire system can use the new data.
