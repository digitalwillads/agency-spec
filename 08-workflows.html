Workflows

Structured multi-step processes for the work you do over and over. Onboarding, campaign launches, tracking installs - codified into repeatable sequences.

What a Workflow Is

Some work is ad hoc - Ruthy emails a question, you answer it, done. But other work follows a known pattern every time. Onboarding a new client always requires the same steps: set up billing, get ad account access, install conversion tracking, create campaigns, launch. Campaign launches always require the same sequence. Platform expansions always require the same prep work.

A workflow is that known pattern, codified. It's a sequence of steps with dependencies - some steps run in parallel, some must wait for others to finish. Each step has clear completion conditions, and the system verifies those conditions are actually met before moving on.

Workflows are not task templates. A task is a single unit of work with a conversation thread. A workflow is an orchestration layer that creates and coordinates multiple tasks, tracks progress across all of them, and ensures nothing falls through the cracks.

Key Distinction
Tasks are individual pieces of work. Workflows are the structure that connects those pieces into a coherent process. A workflow is a parent that spawns child tasks - one per step. When all the child tasks are done (and verified), the workflow is done.

Steps, Dependencies, and Parallelism

Every workflow is defined as a directed graph of steps. Some steps depend on others - you can't launch a campaign before you've built it. Some steps are independent - creative production can happen at the same time as conversion tracking installation. The workflow engine handles this automatically.

Each step in a workflow has:

  • A name - what this step is (e.g., "Install Conversion Tracking")
  • An owner - who is responsible (a specific agent, a team member, or the client)
  • Dependencies - which steps must complete before this one can start
  • Completion conditions - what must be true for this step to be considered done
  • Validation method - how the system verifies the completion conditions are actually met
Example: Step Dependencies

In a New Client Onboarding workflow for Stone & Tile Shoppe:

Step: "Install Conversion Tracking" depends on "Ad Account Access" (you need access to the account to install tracking). But it does NOT depend on "Creative Production" - those can happen at the same time.

Step: "Campaign Launch" depends on BOTH "Install Conversion Tracking" and "Creative Production" - you need working tracking AND finished ads before you go live. The workflow engine won't allow this step to start until both are verified complete.

Step States

Each step in a workflow is always in one of four states:

State Meaning What Happens
Pending Waiting for dependencies to complete No task created yet. The step is visible in the workflow view but grayed out. The system is watching its dependencies.
InProgress All dependencies met, work is active A task has been created and assigned. Someone (an agent, a team member, or the client) is working on it.
Blocked Can't proceed, waiting on something external The step was InProgress but hit a wall. The blocking reason is recorded (e.g., "Waiting on client to provide Google Ads MCC access"). Reporting is notified to follow up.
Complete Done and verified Completion conditions have been checked - either automatically by the system or confirmed by a human. The step is locked. Dependent steps are now eligible to start.
Example: A Step Gets Blocked

ExclusiveMatchmaking is being onboarded. The "Ad Account Access" step is InProgress - we've sent them instructions for granting MCC access to their Google Ads account. Three days pass and they haven't done it.

The step moves to Blocked with reason: "Client has not granted Google Ads MCC access. Instructions sent April 1, no response." Everything downstream - conversion tracking, campaign build, launch - stays Pending.

The Reporting agent is automatically notified. It sends a gentle follow-up to ExclusiveMatchmaking reminding them about the access request. If they don't respond in 3 more days, it escalates (more direct follow-up). If still nothing, it flags you.

Step Validation

This is where workflows differ from a simple checklist. When a step is marked as complete, the system doesn't just take your word for it - it verifies.

Each step has a validation method. Some are automated (the system runs a check). Some require human confirmation. The point is that nothing advances until the completion conditions are actually true, not just claimed to be true.

Step Completion Condition How the System Validates
Billing Setup Client has an active subscription in Stripe Automated: Query Stripe API, confirm subscription status is "active" and first invoice is paid.
Ad Account Access We have admin access to the client's ad accounts Automated: Attempt API call to the ad account. If it returns data, access is confirmed.
Conversion Tracking Pixels/tags are installed and firing correctly Automated: Fire a test event, verify it appears in the ad platform's conversion data within the expected window.
Creative Production All required ad creatives are produced and approved Human confirmation: You or the team member reviews the creatives and marks them approved.
Campaign Launch Campaigns are live and serving impressions Automated: Query ad platform API, confirm campaign status is "ENABLED" and impressions > 0 within 2 hours of launch.
Example: Validation Catches a Problem

Tristan installs the Facebook pixel on TheRealSleep's website and marks the "Conversion Tracking" step as complete. The system runs validation: it fires a test purchase event and waits for it to appear in Facebook's Events Manager.

Nothing shows up. The pixel is on the page but the event trigger is misconfigured - it's firing on page load instead of on form submission.

The step stays InProgress. The system creates a task: "TheRealSleep - Conversion tracking validation failed. Pixel installed but purchase event not firing correctly. Test event sent at 2:15 PM, not received by Facebook after 30 minutes." Tristan fixes the trigger, marks it complete again, and this time the test event goes through. Now the step is truly Complete.

Example Workflow: New Client Onboarding

This is the most common and most important workflow. Every new client goes through it. Here's the full sequence:

Walking through each step:

  1. Contract Signed - The trigger. When a signed contract is detected (via the contract management integration), the workflow kicks off automatically.
  2. Billing Setup - Create the client's Stripe subscription, send the first invoice, confirm payment. Validated: Stripe shows active subscription.
  3. Ad Account Access - Send the client instructions for granting access to their Google Ads, Facebook Ads, or both. Wait for access. Validated: API call to the account succeeds.
  4. Conversion Tracking - Install pixels, tags, and event tracking on the client's website. Validated: test events fire and appear in the ad platform. Runs in parallel with Creative Production.
  5. Creative Production - Create ad copy, images, videos. Get client approval on creatives. Validated: human confirmation that all creatives are approved. Runs in parallel with Conversion Tracking.
  6. Campaign Launch - Build campaigns in the ad platform, set budgets, targeting, and bid strategies. Launch. Validated: campaigns are enabled and serving impressions.
  7. Handoff to Monitoring - The final step. Monitoring rules are activated for this client. The system starts watching their campaigns. See "The Setup-to-Monitoring Handoff" below.
Example: Stone & Tile Onboarding, Day 5

Stone & Tile signed their contract on March 28. Here's where the workflow stands on April 2:

Billing Setup - Complete. Stripe subscription active, first invoice paid March 29.

Ad Account Access - Complete. Google Ads MCC access granted March 30. Facebook Business Manager access granted March 31.

Conversion Tracking - InProgress. Google Ads tag installed and verified. Facebook pixel installed but validation failed - retesting after fix by Isaac.

Creative Production - InProgress. Reileigh has 6 of 8 ad creatives done. Waiting on client approval for the first batch.

Campaign Launch - Pending. Waiting on both Conversion Tracking and Creative Production to complete.

The Setup-to-Monitoring Handoff

This is one of the most important transitions in the system. When campaigns launch, the client shifts from "being set up" to "being managed." The Setup domain's job is done. The Monitoring domain's job begins.

The handoff is not a manual switch. It happens automatically as the final step of any workflow that ends with live campaigns:

  1. Campaign goes live - validated by the workflow engine (campaigns enabled, impressions serving).
  2. Monitoring rules activate - the system registers the client's campaigns with the Monitoring domain. Standard rules are applied: budget pacing, conversion tracking health, performance anomaly detection.
  3. Grace period begins - new campaigns behave erratically in the first 48-72 hours as ad platforms optimize. Monitoring rules start in "observation mode" - they log data but don't alert or auto-fix during the grace period. This prevents a flood of false alarms during the learning phase.
  4. Grace period ends - monitoring rules go fully active. Any anomalies now generate real alerts and auto-fixes.
  5. Timeline entry - the handoff is logged: "Stone & Tile Shoppe - campaigns launched, monitoring active, grace period ends April 5."
Why the Grace Period Matters
Without it, every new campaign launch would generate a wave of alerts. "CPA is $45 when the target is $25!" - yes, because the campaign launched 6 hours ago and has 12 clicks. The grace period lets the platform's algorithms settle before the system starts judging performance. The length is configurable per platform (Google Ads typically needs 7-14 days for Smart Bidding to optimize, Facebook needs 3-5 days for the learning phase).

Progress Visibility

Every active workflow appears as a single parent task in the task system. You don't have to hunt through individual step tasks to understand where an onboarding stands. The parent task is the bird's-eye view.

The parent task shows:

  • Overall progress - "4 of 7 steps complete" with a visual progress bar
  • Current state of each step - which are Complete, InProgress, Blocked, Pending
  • Blockers - any Blocked steps are highlighted with their reason and how long they've been blocked
  • Time tracking - when the workflow started, estimated completion based on current pace, and any steps that are taking longer than expected

You can also ask the AI directly: "Show me all active workflows" or "Where does ExclusiveMatchmaking's onboarding stand?" and get a full status through the chat.

Blocked Steps Notify Reporting

When a workflow step moves to Blocked, the system doesn't just sit and wait. It automatically notifies the Reporting domain, which handles client follow-up.

The flow:

  1. A step moves to Blocked with a reason (e.g., "Client hasn't provided brand assets")
  2. The workflow engine creates a follow-up task in the Reporting domain
  3. Reporting sends the client a gentle reminder after 3 days
  4. If still blocked after 6 days, Reporting sends a more direct follow-up
  5. If still blocked after 10 days, Reporting flags it to you with a recommendation ("ExclusiveMatchmaking has been blocked on ad account access for 10 days. Their onboarding can't progress. Call them?")

The escalation cadence is configurable per client and per step type. Some steps are more urgent than others - a blocked campaign launch gets faster escalation than a blocked creative revision.

Other Workflow Types

New Client Onboarding is the most complex workflow, but it's not the only one. Here are the other standard workflow types:

Campaign Launch

Used when launching new campaigns for an existing client (not a new client onboarding). Steps: campaign strategy approval, creative production, campaign build, QA review, launch, handoff to monitoring. Simpler than onboarding because billing and account access already exist.

Example

Nzymes wants to test video ads on Facebook. Eddie kicks off a Campaign Launch workflow. Reileigh produces the video creatives, Isaac builds the campaign in Ads Manager, you review and approve, it launches, and Monitoring picks it up automatically. The whole process is tracked as one workflow with clear step ownership.

Conversion Tracking Install

Used when installing or reinstalling tracking for a client - either as part of onboarding or because something broke. Steps: audit current tracking setup, install/reinstall tags, configure events, run validation tests, confirm data flowing in ad platform. The validation step is especially rigorous here because bad tracking wastes ad spend silently.

Example

TheRealSleep redesigned their website and the old tracking broke. A Conversion Tracking Install workflow is triggered. The system audits what's missing, Isaac installs the new tags, the system fires test events - purchase, lead form, phone call click - and validates each one. Only when all events are confirmed flowing does the step complete.

Platform Expansion

Used when adding a new advertising platform for an existing client. Steps: platform account setup, conversion tracking for the new platform, creative adaptation (resize/reformat for the new platform's specs), campaign build, launch, handoff to monitoring. Similar to onboarding but scoped to a single platform.

Example

Stone & Tile has been running Google Ads successfully. Now you want to expand to Facebook. The Platform Expansion workflow handles: getting Facebook Business Manager access, installing the Facebook pixel, adapting the existing Google Ads creatives to Facebook specs, building the Facebook campaigns, and launching with monitoring.

Defining New Workflow Types

The workflow types listed above are the starting set. Over time, new patterns will emerge - maybe a "Creative Refresh" workflow when ad fatigue hits across multiple campaigns, or a "Contract Renewal" workflow that coordinates Admin and Reporting 90 days before expiry.

New workflow types are defined by specifying:

  • Steps - what needs to happen, in what order
  • Dependencies - which steps block which
  • Owners - who handles each step (agent, team member, client)
  • Validation methods - how to verify each step is truly done
  • Triggers - what event starts this workflow (manual, or automatic based on a system event)

The architecture is the same regardless of the workflow type. Steps, states, dependencies, validation - it's all the same engine. Only the specific steps and their configuration change.

Design Principle
Workflows should emerge from observed patterns in the work, not be designed speculatively. When you notice the team doing the same sequence of steps for the third time, that's when you define a workflow. The system should make defining new ones straightforward - not a development project.
