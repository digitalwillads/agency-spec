Cross-Agent Intelligence

What happens when agents don't just share data - they consult each other. The difference between a collection of tools and an actual system.

The Concept

Every agent in the system reads from the same timeline and writes to the same task queue. That's coordination - shared data, shared work list. But cross-agent intelligence goes a step further: agents actively query each other during processing.

When the Communication agent is creating a task for a client email, it doesn't just read the timeline. It asks the Monitoring domain: "Are there any active issues with this client's campaigns?" It asks Admin: "Are there any billing issues?" It asks Setup: "Is this client mid-onboarding?" The answers change how the task is created, what context is loaded, and what priority it gets.

This isn't a scheduled batch process. It happens in real time, during the normal flow of work. An agent processing an event makes targeted queries to other domains to enrich its understanding before it acts.

Why This Matters
Without cross-agent queries, each domain operates with tunnel vision. The Communication agent knows about messages. The Monitoring agent knows about campaigns. Admin knows about billing. They can all read the timeline, but they can't ask each other "what's happening right now in your world?" Cross-agent queries close that gap.

Direct Domain Relationships

Not every domain needs to talk to every other domain. The relationships are specific and purposeful. Here are the direct query paths that exist between domains:

Querying Domain Queries What It Asks Why
Admin Reporting "What's the next scheduled communication for this client?" So Admin can alert Reporting to adjust tone before a report goes out to a client with billing issues.
Setup Reporting "This client has a blocked onboarding step. Can you follow up?" So blocked workflow steps trigger client follow-up through the proper channel (Reporting) rather than an ad-hoc message.
Setup Monitoring "Campaigns are live. Activate monitoring rules with a 72-hour grace period." The Setup-to-Monitoring handoff. When a workflow reaches the launch step, Monitoring needs to start watching.
Monitoring Reporting "Here's this client's performance data for the current period." So Reporting can include accurate, up-to-date performance metrics in client reports without duplicating monitoring logic.
Monitoring Communication "Has this client mentioned anything about [campaign/issue] recently?" When Monitoring detects an anomaly, it checks if the client already reported it or if there's context from a recent conversation that explains it.
Communication Monitoring "What's the current state of this client's campaigns?" When a client emails asking about performance, Communication can pull live data to provide context for the response.
Example: A Cross-Agent Query in Action

Ruthy emails: "Hey - I noticed our conversions look low this week. What's going on?"

The Communication agent processes the email. Before creating the task, it queries Monitoring: "Any active issues with Nzymes' conversions?"

Monitoring responds: "Yes - detected a 40% conversion drop on March 30. Root cause: Facebook pixel stopped firing after a website update on March 29. Auto-fix was not possible (requires code change). A task was created for manual fix, currently in progress."

Now when Communication creates the task for Ruthy's email, it includes all of this context. You open the task and see: Ruthy's email, the known conversion issue, the root cause, and what's being done about it. The AI drafts a reply that addresses her question directly: "We caught this too. The website update on the 29th broke the pixel. Isaac is fixing it now, should be back up by end of day." You didn't have to investigate. The cross-agent query already assembled the full picture.

Emergent Properties

The real power of cross-agent intelligence isn't any single query - it's what happens when multiple queries combine during ordinary workflows. The system becomes more than the sum of its parts. Here's a comparison of how common scenarios play out with and without cross-agent queries:

Scenario Without Cross-Agent Queries With Cross-Agent Queries
Client asks about campaign performance Communication creates a task with the email. You open it, pull up Google Ads yourself, check Facebook Ads, look at the timeline for recent changes, piece together the picture manually. Communication queries Monitoring for live performance data, checks for any active alerts, pulls recent changes from the timeline. The task opens with the full picture already assembled: metrics, trends, recent actions, and a draft reply with the numbers.
Conversion drop detected Monitoring creates an alert. Separately, a client email arrives about the same issue. Two independent tasks, no connection between them. Monitoring creates the alert and queries Communication: "Has this client mentioned conversions recently?" Communication, processing the email, queries Monitoring: "Any known issues?" Both tasks are linked. When you open either one, you see the full context: the detected issue, the client's email about it, and the proposed response.
Meeting generates an action item to adjust budget Communication extracts the action item and creates a task. You work the task, manually adjust the budget in Google Ads, manually verify the change. Communication extracts the action item, queries Monitoring for current spend pacing and campaign performance. The task includes: the action item, current budget data, pacing status, and a recommendation on how to implement the change. Monitoring is pre-notified that a budget change is coming so it doesn't fire a false alert.
Overdue invoice detected Admin creates a billing task. The next week, Reporting sends a cheerful performance update completely unaware of the billing problem. Admin creates the billing task AND notifies Reporting. Reporting adjusts the tone of the next outbound communication, includes a mention of the outstanding balance, and holds off on any upsell language. The client gets a message that's professional and aware of the full relationship state.
New client onboarding begins Setup creates the workflow. Each step proceeds independently. If a step gets blocked, nobody follows up until someone notices. Setup creates the workflow. It notifies Monitoring to prepare rules for the eventual campaign launch. It notifies Reporting that this is a new client (first 90 days = weekly reports). When a step gets blocked, Setup queries Reporting to trigger follow-up. When campaigns launch, Setup queries Monitoring to activate rules with a grace period. Every domain knows what's happening and adjusts automatically.

The Network Effect

The math is straightforward. The system has 5 domains. Each domain can query up to 4 others. That's up to 20 possible consultation paths. But the value isn't linear - it's compounding.

Every new domain added to the system doesn't just add its own capabilities - it enriches every other domain's ability to make decisions. When Monitoring gets smarter (new platforms, better anomaly detection), Communication gets smarter too (better answers to client questions about performance). When Admin gets more data (contract details, billing history), Reporting gets more nuanced (better tone adjustment, more informed follow-ups).

This is the network effect. Individual agents are useful. Connected agents are powerful. The connections between domains compound the value of each domain's intelligence.

Example: Compounding Intelligence

A single event - Ruthy's email asking about CPA - triggers a cascade of cross-agent queries:

1. Communication reads the email, queries Monitoring for current CPA data.

2. Monitoring returns the data, plus a note: "CPA improved 17% this week after the negative keyword cleanup."

3. Communication queries Admin: "Any billing issues with Nzymes?" Admin responds: "No issues. Invoice paid on time."

4. Communication queries Setup: "Is Nzymes mid-workflow?" Setup responds: "No active workflows."

5. The task is created with: Ruthy's email, live CPA numbers, the context that the improvement came from a specific action (negative keyword cleanup), clean billing status, and no pending workflow items. The AI drafts a reply that's informed by all five domains. You glance at it, it's perfect, you hit send.

Guardrails

Cross-agent queries are powerful, but they need constraints. Unchecked, they could create cascading loops, performance problems, or opaque decision-making. Here are the guardrails:

Guardrail Rule Why
Read-Only Cross-agent queries are read-only. A querying agent can ask another domain for information, but it cannot modify that domain's state or trigger actions in it. Prevents side effects. When Communication queries Monitoring, it gets data back - it doesn't inadvertently trigger a monitoring action.
Query Budget Each task has a maximum number of cross-agent queries it can make (default: 5). If an agent needs more, it must justify the additional queries. Prevents runaway query chains where one event triggers dozens of cross-domain lookups. Keeps processing efficient and predictable.
One Level Deep Cross-agent queries do not chain. If Communication queries Monitoring, Monitoring answers with its own data. It does not make additional cross-agent queries to answer Communication's question. Prevents circular dependencies and exponential query expansion. A queries B, B answers. B does not query C to answer A. If deeper context is needed, it surfaces as a recommendation for the user.
Graceful Degradation If a cross-agent query fails (timeout, error, unavailable domain), the requesting agent proceeds without that data. It notes the failure in the task context but does not block processing. No single domain failure should cascade to the entire system. If Monitoring is temporarily unavailable, Communication still creates the task - it just lacks the Monitoring context. The user sees a note: "Monitoring data unavailable at time of processing."
Transparency Every cross-agent query is logged. When you open a task, you can see which domains were consulted and what they returned. Nothing is hidden. The user should always understand why the system made a decision. If a task is HIGH priority because Admin reported billing issues, that query and its result are visible in the task's preprocessing details.
Example: Transparency in Practice

You open a task for ExclusiveMatchmaking's email. The preprocessing section shows:

Cross-Agent Queries:

  Monitoring: "Any active issues?" - Response: "No active alerts. Campaigns performing within normal range."

  Admin: "Any billing issues?" - Response: "Invoice #1289 is 15 days overdue ($3,500)."

  Setup: "Active workflows?" - Response: "No active workflows."

You can see exactly why the task was flagged with a billing context note and why the draft reply includes a professional (rather than cheerful) tone. The system's reasoning is fully visible.

Design Principle
Cross-agent intelligence should feel invisible when it works correctly. The user doesn't think "the Communication agent queried Monitoring." They think "oh, the system already knows about the conversion drop when Ruthy asked about it." The guardrails exist to keep the magic reliable without making it fragile.
