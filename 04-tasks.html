The Task System

The universal unit of work. Every piece of work - no matter where it comes from - is a task. Understanding this one concept makes everything else click.

One Task Type

There is one kind of task. Not "email tasks" and "monitoring tasks" and "billing tasks." One kind. Where it came from is metadata - not a different type of object.

This means the system has one queue, one set of priority rules, one lifecycle, one interface. No special cases. When you add a new domain or data source, it creates the same kind of task as everything else. The task model never changes.

Design Philosophy
The task system is like a postal service. It doesn't matter if the letter is a bill, a love letter, or a jury summons - the envelope, the addressing, the delivery route, and the mailbox are all the same. The content varies. The system for moving it doesn't.

Every Task Is a Conversation

A task isn't a card on a kanban board. It's a chat thread. You open it, and you're in a conversation with an AI that already has the context and the tools to resolve it.

This is the core interaction model and it never changes:

  1. Something happens (email arrives, rule fires, meeting generates action items)
  2. An agent creates a task with context attached
  3. The AI preprocesses - reads the timeline, gathers data, may draft a response
  4. You open the task. Context is already there. You work it through conversation.
  5. When resolved, the outcome is logged to the client's timeline

Preprocessing is what makes this fast. You don't start from scratch. For a client email, the AI has already pulled the timeline, checked active tasks, and drafted a reply. For a monitoring alert, it's gathered the data and proposed a fix. You review, adjust, approve, done.

Priority

Every task has a priority that determines its position in the sidebar and whether it can break through the pull model.

LevelWhat QualifiesBehavior
CriticalSite down, account suspended, client threatening to leavePinned to top. Pushes a notification. The one exception to pull-based.
HighClient request needing timely response, approaching deadlineAbove normal in sidebar. No push.
NormalStandard workDefault position
LowFYI, non-urgent admin, backgroundBelow normal. Work when you get to it.

Two Priority Invariants

  • Tasks escalate over time. Unanswered client email for 24+ hours: Normal to High. Worsening monitoring alert: escalates. Aging problems don't stay invisible.
  • User overrides are sticky. If you change a task's priority, the system respects it. It won't re-escalate something you deliberately deprioritized.

Two Lifecycle Invariants

  • Stale tasks re-preprocess. Unworked for 48+ hours? When you open it, the AI re-gathers current data. You never act on a stale snapshot.
  • Completed tasks are searchable forever. Gone from the sidebar, alive in the archive. "What did we do about that Stone & Tile issue last month?" is always answerable.

Deduplication

Multiple agents can notice the same problem. Client emails about low leads while Monitoring detects a conversion drop. One issue, not two.

The principle: one issue, one task. When two tasks match on the same client, similar timeframe, and related issue, they merge. Both trigger sources are visible in the merged task.

When Dedup Is Wrong

  • Split - incorrectly merged? Pull them apart. Each keeps original context.
  • Merge - missed a connection? Combine two tasks into one.

The system's dedup is a best guess. The user is the final authority.

What Never Changes

As the system grows - new domains, new agents, new data sources, new tools - the task system stays the same:

  • One task type. Source is metadata.
  • Every task is a conversation thread.
  • Every task has a priority that can escalate.
  • Every task moves through the same lifecycle.
  • Every completed task is logged to the timeline.
  • The user can always override, split, merge, defer, or reassign.

If a new capability can't express its work as a task, something is wrong with how the capability was designed - not with the task system.
